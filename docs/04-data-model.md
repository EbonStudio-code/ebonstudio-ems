# 04. PostgreSQL Data Model

**Implemented schema:** `apps/api/migrations/001_create_users.sql` and `002_backend.sql`. The original MongoDB/ObjectId design is superseded. SQL definitions, not this summary, are authoritative. The user's local database still needs the reviewed migration-002 upgrade described in [Backend setup](14-backend-implementation.md).

## 1. Conventions

- UUID primary keys generated by PostgreSQL; IDs are opaque strings in the API.
- UTC `TIMESTAMPTZ` instants; company-local `DATE`/`DATE[]` values returned as `YYYY-MM-DD`. Salary periods are validated `YYYY-MM`.
- ISO currency code plus explicit minor-unit exponent. Monetary inputs and computed totals are safe integer minor units.
- Tables/columns use snake_case; public DTOs use camelCase. Mutable business records expose `version`.
- Foreign keys enforce references without cascading historical deletes.
- One company and one CEO after bootstrap; no tenant-ID pretense or hidden HR/manager roles.
- Business-history erasure/retention is not automated. Holidays may be removed with the required safeguards; only expiring security records have a cleanup command.

## 2. Core tables

### `schema_migrations`

Migration filename, SHA-256 and applied timestamp. The migration owner writes it; runtime only reads. Existing manual 001 requires explicit baseline plus exact catalog comparison. Startup never applies migrations.

### `users`

UUID; unique canonical email; role CEO/EMPLOYEE; status INVITED/ACTIVE/SUSPENDED; password_hash; ceo_display_name; session_version; invitation/activation/login timestamps; created/updated timestamps and version.

Canonical email is trimmed/lowercase, without provider-specific dot removal. Passwords are Argon2id hashes and absent until setup. A partial unique index permits at most one CEO. Controlled bootstrap establishes the first CEO; there is no CEO promotion/deletion endpoint.

### `company_settings`

A checked boolean singleton primary key, identity/legal/address fields, IANA timezone, working_weekdays, currency_code/minor_unit, leave_types, salary_publication_enabled, salary_jurisdiction, calendar_revision, calendar_guard, version and timestamps.

No business values are seeded. API validation requires unique weekdays 0–6, valid timezone/currency precision and nonempty leave labels. Timezone/workweek lock once any attendance/leave exists. Currency locks after the first draft. Salary publication additionally requires reviewed legal name/address/jurisdiction.

Public settings omit the singleton key and internal guard. An initial PATCH uses version 0 and stores version 1.

### `sessions`

Hashed session token primary key, hashed CSRF material, optional user reference/session_version, created_at, expires_at and absolute_expires_at.

Idle lifetime is 30 minutes; absolute lifetime is 8 hours. The server checks expiry/status/version independently of cleanup. Indexes cover expiry and user revocation. Raw cookie/CSRF tokens never enter database rows.

### `account_tokens`

UUID, user reference, purpose INVITATION/PASSWORD_RESET, unique token_hash, expires_at, consumed_at, delivery_status and created_at.

Invitation lifetime: 24 hours. Reset lifetime: 30 minutes. Redemption/resend invalidates outstanding account tokens. Only hashes are stored in PostgreSQL. Explicit local preview mail files contain the sensitive raw link; they are separate ignored artifacts, not database/log records.

### `rate_limits`

HMAC key, count and expiry. SQL UPSERT atomically starts/increments windows. All production instances share a stable secret. Decisions enforce expiry before cleanup; raw email/IP values are not stored as counter keys or logged.

### `audit_events`

UUID, optional actor user, module, action, optional entity UUID, request UUID, bounded optional reason and created_at.

No full payloads, password/session/token material, complaint bodies or salary amounts. Audit inserts participate in domain transactions. UPDATE/DELETE triggers reject history edits, and runtime only has SELECT/INSERT. A privileged database owner can still bypass controls; this is not externally tamper-proof storage.

## 4. Attendance and leave semantics

- Work date remains the original company-local check-in date across midnight.
- Punch flags remain historical. `currentApprovedLeaveOverlap` is a live read projection, not an update to old flags.
- Corrections retain prior/next timestamps/state/version; they cannot change owner/work date or create a missing attendance record.
- Leave API calls the stored array `workingDatesSnapshot` and the revision `calendarRevisionAtSubmission`.
- Pending/Approved requests retain reservations. Rejection/cancellation releases them in the same transaction as state/history/audit.
- Holidays affect new calculations only. A calendar guard fingerprint prevents stale impact acknowledgements.
- Start-date edits cannot invalidate existing attendance or leave. A global domain-write advisory lock coordinates these checks with employee deactivation.

## 5. Salary data

Each line has `{ label, amountMinor }`. At least one earning, maximum 20 earning and 20 deduction lines; per-line ceiling 1,000,000,000,000 minor units. Server sums must be safe integers and deductions cannot exceed gross.

Physical `gross`, `deduction_total`, `net` are BIGINT with checks. API names are `grossMinor`, `totalDeductionsMinor`, `netMinor`, safely represented as numbers within supported bounds.

Drafts use current employee/company details for preview. Publication captures JSONB snapshots of employee name/code/job/department and company name/legal/address/jurisdiction, plus retained template version 1. Published values/snapshots cannot change. The database trigger permits only PUBLISHED → VOIDED with reason/actor/time/version advancement. VOIDED rows remain immutable.

A replacement is a new UUID and increasing revision. One draft may coexist with one published statement, but the current statement must be voided before publishing the replacement. Employees can read/download only their own PUBLISHED/VOIDED rows, never drafts. Inactive former employees cannot log in even when the CEO publishes a final statement.

## 6. Integrity and access

| Invariant | Enforcement |
| --- | --- |
| Single CEO; no duplicate account/code | Unique/partial indexes and controlled workflows |
| Account/profile and mandatory audit commit together | PostgreSQL transaction |
| Deactivation cannot race with new/reopened blockers | Shared transaction advisory lock plus eligibility/blocker checks |
| Daily/open attendance and reserved leave uniqueness | Database unique indexes and state checks |
| Stale edits cannot overwrite current state | Public version checks under the domain lock |
| Preview cannot silently become stale | Calendar guard and bound operation fingerprint |
| Published statement cannot be rewritten | State-aware API plus immutable database trigger |
| Audit/corrections/messages/history are append-only | Restricted runtime grants plus triggers |
| Disabled feature data retains its protection | Guards still inspect retained tables |

The runtime role receives only required table operations, no schema CREATE or migration writes. Broad historical DELETE grants are not given. Review pre-existing role memberships/ownership separately; the grants script does not revoke unrelated permissions.

## 7. Migration and performance policy

Run explicit owner migrations and then runtime grants. Do not edit an applied migration: checksums reject drift. Back up first; there is no automatic destructive rollback/reset command.

Actual indexes are in SQL, not a claim of tuned performance. At this stage domain writes are globally serialized and directory search is a bounded escaped substring search. Query-plan/load tests on representative history, backup restore and a production database permission/TLS review remain release gates.
